# Хакатон RLT.Университет (Росэлторг), СПб, 1–2.10.2026

Сервис подбора релевантных поставщиков, производителей и дистрибьюторов для АИС ГЗ и
электронного магазина Санкт-Петербурга. Вход — закупка (лот), выход — ранжированный список
контрагентов с ролью, статусом и объяснением.

Команда: один человек. Исходники брифинга: `docs/presentation.pdf`, `docs/briefing_transcript.txt`
(расшифровка аудио, местами искажена).

## Критерии (100 баллов)

| Критерий | Баллы |
|---|---|
| Работоспособность и целостность решения | 30 |
| Качество рекомендаций | 25 |
| Обогащение и расширение пула (новые компании, классификация ролей, достоверность) | 25 |
| Объяснимость (почему рекомендован и почему такой статус) | 10 |
| Интерфейс и UX | 10 |

## Жёсткие условия

- Внешние API нейросетей (GPT, GigaChat и т.п.) запрещены в логике работающей системы.
  При разработке — можно. API поисковиков — можно. Локальные модели — уточнить на чекпоинте.
- Подбор должен отвечать за секунды: 5–10 с допустимо, 30 с — нет. Предрасчитывать индексы.
- Обогащение — офлайн, не в реальном времени. Обязательно фиксировать источник каждой записи.
- Защита ~5 минут, 3–5 живых кейсов. Интерфейс не должен съедать время: он стоит 10 баллов.
- 10 новых поставщиков в обогащении — слабо; ориентир со слов спикера — порядка сотни и больше.

## Данные (`data/raw/`, в git не попадают)

CSV, UTF-8, разделитель `;`, строки в кавычках `"` с удвоением. Связь — по `lot_id`.
ИНН/КПП читать как строки (бывают 12-значные ИНН ИП, ведущие нули).

- `notices.csv` (~604 тыс. строк) — извещения, одна строка = один лот:
  `publish_date; procedure_id; lot_id; start_price; reqnum; procedure_name; subject; is_smp; customer_inn; customer_kpp; is_eshop_or_aisgz`
  (`is_eshop_or_aisgz`: «АИС ГЗ» или «ЭМ»).
- `tru.csv` (~2,97 млн строк) — позиции лота: `lot_id; product_name; okpd2_code`.
- `suppliers.csv` (~1,01 млн строк) — участники: `lot_id; supplier_inn; supplier_kpp; is_winner`
  (`false` = участвовал, но не победил).

Оригинальные имена в архиве: `Извещения_24-25.csv`, `ТРУ_24-25.csv`, `Поставщики_24-25.csv`.

Загрузка: `python scripts/load.py` → `data/rlt.duckdb` (таблицы `notices`, `tru`, `suppliers`;
`is_eshop_or_aisgz` переименован в `source`). Разведка — `docs/eda.md`. Главное оттуда:

- В АИС ГЗ у лота всегда один участник (победитель), у 16% лотов участников нет вовсе.
  Конкуренция видна только в ЭМ (2,69 участника на лот). `is_smp` в ЭМ всегда `false`.
- У ИП нет КПП (пусто или `000000000`) — регион брать из первых цифр ИНН.
- ~7,4 тыс. 12-значных ИНН — физлица-преподаватели (класс 85, только АИС ГЗ): не рынок.
- ОКПД2 разной глубины (5% кодов короче 9 знаков) — работать по префиксам.
- Дубли: 31 пара лот–поставщик, ~165 тыс. групп одинаковых позиций в tru.
- Отсечка для метрики: 2025-10-31; 96% заявок после неё — от уже известных поставщиков.

Тестовый набор организаторов (02.10.2026): `Тестовый датасет_извещения_20261002.csv` и
`…_потоварка_…csv` в `data/raw/` — 38 процедур за январь–август 2026 без участников, формат
как у `notices.csv` и `tru.csv`. Порядок: `python scripts/add_procedures.py` (дописывает лоты в
`notices`/`tru`, номера — в таблицу `test_lots`; сервер на это время остановить) →
`python -m recsys.build` → `python -m recsys.pool` → `python scripts/predict.py` →
`data/out/test_recommendations.csv` (топ-10 из истории и 5 новых компаний на лот, с ролью,
статусом и причинами). Обогащение перезапускать не нужно. `scripts/load.py` тестовые лоты стирает.
В интерфейсе тестовые лоты открываются по номеру, как обычные; семь из них — константа
`TEST_LOTS` в `app/main.py` — вынесены на страницу строкой «Тестовый набор» над примерами
«Из истории» (`DEMO_LOTS`); в `/api/examples` у них `test: true`. Из-за них «сегодня» для новой
закупки, введённой руками, — 12.08.2026 (день после последнего лота в индексе).

## Код

- `python -m recsys.build` → `data/index.pkl` (~40 с): постинги заявок по префиксам ОКПД2,
  по заказчикам, по лотам + TF-IDF. Агрегатов «на все времена» в индексе нет.
- `recsys/recommender.py` — `Recommender.score()/recommend()`: признаки считаются при запросе
  с отсечкой по дате (история строго раньше дня запроса), ~40 мс на лот. Общие профили
  поставщика (число заявок, типичная цена, доля АИС ГЗ, победы в СМП) — тоже на день запроса:
  `Recommender.profiles(day)`, ~60 мс, кэш по дням. Итог =
  релевантность (ОКПД2 на 4 уровнях, текст, заказчик) × (1 + цена, регион, специализация,
  площадка, СМП). Веса и параметры — константы в начале файла, подобраны `scripts/tune.py`.
  Физлица-преподаватели исключены из выдачи.
- `scripts/try_lot.py <lot_id | текст>` — подбор руками, с местами реальных участников.
- `scripts/evaluate.py [N] [дата]` — Recall@10 / MAP@10 на лотах после отсечки (полный подбор).
- `scripts/tune.py` — подбор весов (настройка: сен–окт 2025, проверка: ноя–дек 2025) и таблица
  вклада факторов; признаки кэшируются в `data/tune_cache_*.pkl`. `scripts/tune_sweep.py` —
  перебор параметров признаков.

Метрика (`docs/metrics.md`): 5 923 лота после 2025-10-31 — Recall@10 0,656, победитель в
топ-10 0,671, MAP@10 0,447. Основной фактор — текст (один даёт 0,639; без него 0,474);
только полный код ОКПД2 — 0,397; десять самых активных поставщиков — 0,048. Подкрутка весов
исчерпана (разброс вариантов в пределах шума ~0,01).

Обогащение (`docs/enrichment.md`, порядок запуска там же), всё офлайн:

- `enrich/rmsp.py`, `fns.py`, `rnp.py` → таблицы `rmsp`, `fns_headcount`, `fns_revexp`, `fns_debt`,
  `rnp`; архивы ФНС в `data/ext/`. `enrich/companies.py` → таблица `companies` (одна строка на
  ИНН: 44 тыс. известных + 464 тыс. новых из СПб и ЛО; название, роль с обоснованием, сигналы
  достоверности, источники) и `data/out/companies.csv`.
- `recsys/pool.py` → `data/pool.pkl`; `Pool.recommend(codes, vec)` подбирает новые компании по
  связи ОКВЭД→ОКПД2, выученной из истории, совпадению ОКВЭД, тексту и достоверности (~50 мс).
  Выдаётся отдельным списком. Проверка способа — `scripts/validate_pool.py`.
- Статус (`docs/statuses.md`) считается там же, в `enrich/companies.py`: риск (РНП) → требует
  проверки (долг > 100 тыс. или юрлицо не найдено в реестрах) → проверенный (3+ победы) →
  участник → новый, подтверждён → новый. Роль: производитель (ОКВЭД 01–32), дистрибьютор
  (46 и 45, кроме 45.2), поставщик.
- `recsys/explain.py` — причины и разбивка балла из тех же чисел, что и балл.
  `recsys/service.py` — `Service.by_lot()/by_input()`: полный ответ (карточки, роли, статусы,
  объяснения, новые компании, места реальных участников), ~300 мс. API строить поверх него.
- Запуск: `python -m uvicorn app.main:app --port 8010` (порт 8000 на этой машине занят),
  страница — http://127.0.0.1:8010/, прямая ссылка на лот — `/#lot=6008824`.
  `app/main.py`: `GET /api/lot/{id}`, `POST /api/recommend`, `GET /api/search?q=`,
  `/api/examples`, `/api/stats`. Цифры качества (экран «Качество и источники») заданы константой
  `QUALITY` в `app/main.py` — обновлять вместе с `docs/metrics.md`.
- Сервер — `docs/deploy.md`: `docker compose up -d --build`, данные (`index.pkl`, `pool.pkl`,
  `rlt.duckdb`) копируются в `data/` отдельно и монтируются на чтение. Версии в
  `requirements.txt` закреплены под pickle-индексы — менять вместе с пересборкой индексов.
- Фронт — React + TypeScript (strict) + Vite в `web/`. FastAPI отдаёт сборку `web/dist` (в git
  не попадает): после правок и на новой машине — `cd web && npm install && npm run build`
  (сборка сначала гоняет `tsc --noEmit`; отдельно — `npm run typecheck`). Разработка —
  `npm run dev` (запросы `/api` проксируются на порт 8010). Шрифты и иконки вшиты в сборку.
  - `web/src/types.ts` — типы ответов API; менять вместе с `Service._build` и `CARD_COLUMNS`
    в `recsys/service.py`. Поля компании из реестров бывают пустыми — в типах они необязательные.
  - `web/src/ds/` — дизайн-система «Нева» (claude.ai/design, проект
    `a7e61ff3-2d77-410d-bfb5-ab23928267ff`): токены в `styles.css`, компоненты перенесены как есть.
    Отличия от исходника: `Icon` берёт SVG из пакета `lucide-static` (список иконок — в файле),
    `AppHeader` без «Справки» и уведомлений, `StatusBadge` знает наши статусы, у `MatchScore`
    есть `unit`. Правила текста и оформления — в readme проекта дизайн-системы.
  - `web/src/screens/` — подбор (`SearchScreen`), карточка компании (`SupplierProfile`),
    сравнение (`CompareScreen`), качество и источники (`AboutScreen`); состояние — в `App.tsx`.
  - Телефон: стили компонентов заданы в `style`, поэтому адаптация — классами `neva-*`/`app-*`
    и правилами `@media` с `!important` в конце `ds/styles.css` (≤960 px и ≤640 px), а где нужно
    менять содержимое (подписи вкладок, набор колонок таблиц) — хуком `useNarrow()` из `lib.ts`.
    Граница 640 px в хуке и в CSS должна совпадать.
  - Экранов «Запросы КП», «Избранное», «Аналитика цен» и переключателя «ИИ-подбор» из макета
    нет намеренно: под ними нет данных, а нейросетей в подборе нет.
- Защита — `docs/defense.md`: сценарий на 5 минут, цифры одной таблицей, ответы на вопросы.
  Кейсы — константа `DEMO_LOTS` в `app/main.py` (кнопки «Примеры» на странице): бумага 5964926,
  лифты 6038385 (победитель со статусом «риск»), ноутбуки 5953570, тетради 6026673 (АИС ГЗ, СМП),
  5959879, 6019464, трудный случай 5954657.
- Несделанное — в `docs/backlog.md`: ГИСП (403, защита от ботов — не обходить, нужна ручная
  выгрузка), неполный РНП по 44-ФЗ (лимит поиска ЕИС 5 000 записей), статус из ЕГРЮЛ.
- База DuckDB однопользовательская на запись: пока идёт `enrich.*`, читать её нельзя.

## Стек

Python, FastAPI, DuckDB, фронт на React + TypeScript (Vite, одна страница). Текстовая близость — TF-IDF/BM25 локально.

## План

1. Разведка данных: объёмы, пропуски, битые ИНН, распределение по ОКПД2, участников на лот, даты.
2. Базовый подбор: кандидаты по ОКПД2 (разные уровни иерархии) + текстовая близость названий
   с весами редких слов; ранжирование по победам/участиям в категории, истории с заказчиком,
   ценовому диапазону, СМП, региону (первые цифры КПП), свежести.
3. Метрика: разбиение по `publish_date`, скрыть участников отложенных лотов, Recall@10 / MAP
   по реальным участникам и победителям. Число нужно для защиты.
4. Обогащение (офлайн): ЕГРЮЛ/ОКВЭД (ФНС), реестр МСП, реестр промышленной продукции
   Минпромторга (ГИСП) — производители, реестр контрактов ЕИС, РНП — отрицательный сигнал.
   Роль — правилами (ОКВЭД: раздел C — производитель, 46 — дистрибьютор; наличие в ГИСП).
5. Статусы и объяснения: статус контрагента + разбивка балла по факторам человеческим языком.
6. API и интерфейс: поиск по `lot_id` или ввод новой закупки, список с ролями, статусами, «почему».
7. Защита: 3–5 разных кейсов, метрика, список источников, число новых компаний.
